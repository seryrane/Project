# 기획 가이드 — 다음 화면을 설계하기 전에

> **누구를 위한 문서인가**: 코드를 모르지만 화면과 업무 흐름을 설계하는 기획자.
> **무엇의 정본인가**: 화면을 새로 기획할 때 "이건 어디서 확인하지?"에 답하는 지도 —
> 화면 목록·업무 흐름·권한을 사람 말로·용어집이 이 문서의 정본이다.
> **정본이 아닌 것**: 화면 배치·알림 규칙은 `docs/화면_공통규칙.md`, 권한 구조는
> `docs/RBAC_설계노트.md`, 사업 배경·요구사항은 `docs/PROJECT_CONTEXT.md` 가 정본이다.
> 이 문서는 그 세 문서를 기획 관점에서 요약하고 가리킬 뿐, 내용을 다시 정의하지 않는다.

---

## 0. 먼저 — 낱말 사용 주의

이 포털은 **두 사업의 합본**이다. 프로젝트는 하나(슬로건: One Portal, One Login, One
User, Many Services)지만, RFP 도 두 벌이고 **메뉴가 두 사업을 가른다.**

| 사업 | 정식 명칭 | 이 문서·코드에서 부르는 이름 |
| --- | --- | --- |
| 센터 KPI 품질 관리 | **ICDAP** | 메뉴 섹션 "센터 KPI (ICDAP)" |
| IBD 수집사양 관리·검증 | **IDMS** | 메뉴 섹션 "사양서 (IDMS)" (+ 검증엔진) |

⚠ **어느 한쪽 낱말로 포털 전체를 부르지 않는다.** "사양관리 시스템"이라고 부르면 ICDAP
쪽 화면(KPI 대시보드·IVI)이 없는 것처럼 들리고, "KPI 포털"이라고 부르면 IDMS 쪽
(사양서·승인·배포·검증)이 빠진 것처럼 들린다. 화면 기획서·회의록에도 이 구분을 그대로
쓴다. (근거: `docs/PROJECT_CONTEXT.md` 1절, `frontend/src/data/nav.ts` 코드 주석
— "이 포털은 두 프로젝트의 합본이다 … 메뉴가 두 프로젝트를 가른다")

## 1. 이 포털이 무엇인가

```
                        HMG 통합 관리자 포털
          (One Portal, One Login, One User, Many Services)
 ┌──────────────────────────────────────────────────────────────┐
 │  공통 기반 — 로그인·회원·권한(RBAC)·메뉴·알림·감사로그·커뮤니티      │
 │  (SSO 프로토콜 미정 · JWT 정책 미정 · 조직/메뉴 동적 등록)          │
 └───────────────────────┬──────────────────────┬────────────────┘
                          │                      │
        ┌─────────────────▼───────────┐  ┌───────▼─────────────────────┐
        │   센터 KPI (ICDAP)            │  │   사양서 (IDMS)                │
        │   센터 KPI 품질 관리 사업        │  │   Connect IBD2.0 사양서 관리/검증│
        │                              │  │                              │
        │ · 센터 KPI 대시보드 (analytics) │  │ · 사양서 관리 / 상세             │
        │ · 인포 IVI KPI (kpi-ivi)      │  │ · 승인 관리 (결재)               │
        │ · 지표 관리 (kpi-metrics)      │  │ · 배포 관리                    │
        │                              │  │ · 검증엔진 관리 / 결과 / 리포트    │
        └──────────────────────────────┘  └──────────────────────────────┘
             LNB 섹션 "센터 KPI (ICDAP)"        LNB 섹션 "사양서 (IDMS)" + "검증엔진"
```

- **가르는 주체는 메뉴다.** 데이터베이스·인증·공통 프레임워크는 공유하고, 좌측
  내비게이션(LNB)의 섹션 제목이 사용자에게 "지금 어느 사업 화면인가"를 알려주는
  유일한 표시다. 새 화면을 넣을 때도 반드시 두 섹션 중 하나(또는 공통 섹션: 관리·
  커뮤니티·시스템) 아래 놓는다 — 어디에도 안 속하는 화면은 만들지 않는다.
- **일정**: 2026년 10월 착수 ~ 2027년 4월, 총 4단계 오픈(현재는 요구사항 확정 전
  프로토타입 단계). 자세한 사업 배경·기술 스택은 `docs/PROJECT_CONTEXT.md` 참고.

## 3. 업무 흐름 — 사양서의 일생

IDMS 쪽 사양서는 작성부터 리포트까지 화면 다섯 개를 순서대로 지나간다.

```
[사양서 관리/상세]        [승인 관리]              [배포 관리]                  [검증엔진]                  [검증 리포트]
  초안 → 수정중            결재 상신                개발 → 검증(Staging)          Rule 실행                  결과 기반 생성
  → 임시저장 → 최종완료  ─▶ N단계 결재            ─▶ → 승인 → 운영(Production) ─▶ (배치/실시간, 일 10만건+) ─▶ → 발행/조회
  → 승인요청              (대결·참조·반려/재상신)     승인 확정 시에만 배포됨        오류 분류·재처리            Excel/PDF, 대시보드
      │                        │                         │                          │                          │
   Editor 가 쓴다          승인권자가 처리           Admin 이상이 실행/승인       Admin 이상이 관리/실행       Admin·Editor 가 본다
   (역할 4종 중 조회+       (역할 4종 중 "승인"        (배포는 되돌리기 어려운       (Rule 변경은 Admin,          (임시저장→발행 상태 있음)
    생성+수정 있는 역할)     액션이 있는 역할)          동작 — 확인 모달 대상)        조회는 더 넓게 허용)
```

- **워크플로 단계 이름은 코드 정본(`data/specFields.ts` WORKFLOW_STEPS)이 갖고 있다**:
  초안 · 수정중 · 임시저장 · 최종완료 · 승인요청 · 배포승인 · 배포완료. 새 상태를
  만들 필요가 있으면 여기에 먼저 추가하고 화면은 그 값을 그린다(화면이 스스로 상태
  이름을 짓지 않는다).
- **최종 반영 전 관리자 승인은 필수**다(`PROJECT_CONTEXT.md` §4) — 승인 관리를 건너
  뛰고 배포 관리에서 바로 반영되는 경로는 없다.
- **동일 사양 다중 수정 요청의 충돌 관리**(2026-08-21 구현). 같은 사양서에 변경 요청이
  둘 이상 겹칠 수 있다 — **막지 않는다**. 겹치면 승인 관리에서 그 건들이 붙어 서고
  `겹침 n` 배지가 붙으며, **배포 요청만** 막힌다. 하나를 고르고 나머지는 사유를 내고
  **취소**한다(취소 ≠ 반려 ≠ 회수 — 셋의 뜻이 다르다, §8 참고).
  ⚠ 근거는 요구사항정의서가 아니라 **2026-07-20 회의록**이다.
- 승인 대상은 사양서만이 아니다. `data/approvals.ts` 기준 결재 종류는 **사양서·배포·
  메뉴·권한** 네 가지 — 승인 관리 화면은 이 넷을 한 화면에서 같이 다룬다.

## 4. 권한을 사람 말로

정본은 `docs/RBAC_설계노트.md`. 여기서는 화면을 기획할 때 바로 쓸 수 있게 요점만 옮긴다.

### 역할 4종 — "무엇을 할 수 있나"

| 역할 | 한 줄 요약 |
| --- | --- |
| Super Admin | 전체 시스템 관리 — 회원·권한·메뉴 관리까지 포함한 최상위 권한 |
| Admin | 서비스 운영·모니터링 권한 — 배포·검증엔진 운영, 승인 처리 |
| Editor | 사양서 작성·수정 권한, 승인 요청(상신)까지 가능. 승인 자체는 못 한다 |
| Viewer | 사양서·지표 **조회 전용** |

### 왜 "조회 범위" 축이 따로 있나

**화면에 들어갈 수 있는가**(메뉴가 보이는가)와 **무엇까지 보이는가**(내 데이터인지 전사
데이터인지)는 다른 질문이다. 그래서 권한은 `동사.자원.범위` 세 겹으로 본다 — 예:
`사양서.조회.team`(우리 팀 사양서까지 조회).

```
범위:  own(내 것만)  <  team(우리 팀)  <  all(전체)
       넓은 것이 좁은 것을 자동 포함한다 — 포함 판단은 서버 한 곳에서만.
```

같은 "사양서 관리" 메뉴를 Editor 는 팀 범위로, Viewer 도 팀 범위로 보지만(하지만
Viewer 는 조회·다운로드만 되고 생성·수정은 안 됨), Super Admin 은 범위 지정이 없으면
전체로 본다. **화면을 새로 만들 때 이 두 축(메뉴 접근 여부 / 조회 범위)을 항상 같이
정한다** — 범위를 나중에 붙이면 조회 API 를 전부 다시 손대야 한다.

### "메뉴를 준다 ≠ 권한을 준다"

메뉴가 LNB 에 보인다고 그 화면의 모든 동작이 되는 것은 아니다. **보이는 것과 되는
것을 나눈다** — 예를 들어 승인 관리 메뉴는 Editor 에게도 보이지만(조회는 됨), "승인"
버튼은 Editor 에게 없다(비활성 또는 아예 안 보임). 눌러서 "권한이 없습니다"가 뜨는
것은 나쁜 화면이다 — 애초에 못 누르게 그린다.

### 자기 잠금 방지

관리자가 실수로 자기 역할에서 [권한 관리] 액션을 빼면, 회사 안 누구도 되돌릴 수 없는
상태가 된다. 그래서 저장 전에 "그 권한을 가진 사람이 몇 명 남는지"를 세고, 0명이 되는
변경은 **접수 자체를 거절**한다(권한 관리 화면에서 실제로 지키는 규칙). 새 화면에서
권한을 회수하는 동작을 만들 때는 이 검사를 빼먹지 않는다.

### 최소 메뉴

공지·Q&A·FAQ·가이드처럼 **권한과 무관하게 모든 역할이 보는 메뉴**를 "최소 메뉴"라
부른다(`data/menus.ts` 의 `minimal: true`). 권한으로만 메뉴를 가리면 Viewer 처럼
권한이 적은 역할은 LNB 가 텅 비어 "로그인해도 볼 게 없는 포털"이 된다 — 특히 가이드는
권한이 없는 사람일수록 "나는 무엇을 할 수 있나"가 궁금하므로 여기에 권한을 걸지
않는다.

## 5. 화면을 설계할 때 먼저 정할 것

정본은 `docs/화면_공통규칙.md` — 화면을 만들기 전에 반드시 먼저 읽는 문서다. 여기서는
그 결정을 **기획 언어로 압축한 판단표**만 둔다.

### 이 기능은 어디에 뜨나 — 표시 영역 4종

```
                  머무는 시간
                  짧다 ──────────────────────▶ 길다
   본문과   따로   │  MODAL          │  MAIN
   함께     ───────┼─────────────────┼──────────────
   봐야     같이   │  BOTTOM         │  RIGHT
   하나?           │  (흐르는 것)     │  (대조하는 것)
```

| 물어볼 질문 | 답이 "그렇다"면 |
| --- | --- |
| 그 자체가 5초 넘게 붙어 일하는 화면인가? | **MAIN**(본문 페이지) — 예: 사양서 상세, KPI 대시보드 |
| 목록을 훑으며 본문과 대조해서 봐야 하나? | **RIGHT**(우측 패널, 덮되 가리지 않음) — 예: 버전 이력 |
| 시간순으로 흐르다 끝나면 안 봐도 되나? | **BOTTOM**(하단 콘솔/시트) — 예: 검증 실행 로그 |
| 5초 안에 끝내고 닫는 동작인가? | **MODAL** — 예: 승인 요청 확인, 사양서 신규 등록 |

### 이 알림은 무엇인가 — 알림 4종

```
되돌릴 수 없나? ──예──▶ 확인 모달 (무엇이 사라지는지 문장으로)
      │아니오
방금 한 일의 결과인가? ──예──▶ 성공: 토스트(+되돌리기) / 실패: 인라인
      │아니오
특정 입력 때문인가? ──예──▶ 인라인
      │아니오
      └──▶ 배너 (연결 끊김·권한 없음·설정 필요)
```

- **되돌릴 수 없는 동작**(삭제·승인·반려·배포)에만 확인 모달을 쓴다. 남발하면 정말
  위험한 순간에도 사람이 안 읽고 누른다.
- **되돌릴 수 있으면 묻지 말고 되돌릴 길을 준다** — `"완료 처리했습니다 [실행 취소]"`
  가 매번 묻는 확인 모달보다 낫다.

### 기획서에 반드시 적어야 하는 것

새 화면·새 기능을 기획서에 적을 때, 위 두 판단(표시 영역 / 알림 종류)과 함께
**"되돌릴 수 있는 동작인가"**를 한 줄로 명시한다. 이 한 줄이 퍼블리셔·개발자가
구현 방식을 고르는 유일한 근거가 된다 — 없으면 화면마다 다르게 구현되고, 그 순간부터
사용자는 "예측"이 아니라 "시도"로 화면을 쓰게 된다(`화면_공통규칙.md` 0절).

## 6. 다국어를 전제로 기획한다

한국어·영어 두 언어 지원이 **요구사항**이다(IVI 다국어, 글로벌 조직 대응). 정본은
`docs/화면_공통규칙.md` §4. 기획서를 쓸 때 다음을 같이 적어야 나중에 다시 뜯지 않는다.

1. **상태 이름은 코드 + 표시명으로 나눠 정의한다.** 기획서에 "승인 대기"라고만 적지
   말고 `PENDING = 승인 대기 / Pending Approval` 처럼 짝으로 적는다 — 서버가 문장이
   아니라 재료(코드)를 주고 화면이 번역하는 구조라서다.
2. **숫자가 낀 문구는 파라미터로 적는다.** "오늘 5건"이 아니라 "오늘 **{n}**건" —
   영어는 복수형이 있어 문장을 통째로 저장하면 사전이 성립하지 않는다.
3. **메뉴 이름의 영문명은 관리자가 메뉴 관리 화면에서 직접 넣는다.** 개발이 넣는 기본
   번역은 있지만, 정본은 그 관리자 입력값이다 — 기획서에서 "이 메뉴의 영문명은 OO"라고
   미리 못 박지 않는다(관리자가 나중에 바꿀 수 있는 값이라는 것만 전달한다).
4. **영문은 한글의 1.5~2배 길다.** 짧은 라벨을 요구하는 자리(LNB·표 셀·카드 제목·탭)에
   긴 한글 문구를 쓰지 않는다 — 한글로는 맞아도 영어로 바꾸는 순간 터진다. 기획서에
   "라벨은 한글 6자, 영문 10자 이내"처럼 길이 상한을 같이 적어 주면 좋다.

| 최소 메뉴 | 권한 없이도 모든 역할에 보이는 메뉴(공지·Q&A·FAQ·가이드) | "누구나 편집 가능"이 아니다 — 보이는 것(메뉴)과 되는 것(쓰기 권한)은 여전히 분리됨 |

## 9. 프로토타입을 볼 때 유의할 것

- **전부 목데이터(mock data)다.** `frontend/src/data/*.ts` 에 있는 회원·사양서·승인
  건수는 화면 시연용 고정 값이지 실제 운영 데이터가 아니다.
- **서버가 있으면 서버 값, 없으면 mock 으로 조용히 전환된다.** 일부 화면(공지·Q&A·
  FAQ·회원 등)은 `backend-python` 서버가 떠 있으면 그 값을 쓰고, 서버가 없으면 화면이
  알아서 mock 데이터로 돌아간다(시연 안전장치, `frontend/src/lib/api.ts`가 그 관문).
  즉 같은 화면이라도 서버 기동 여부에 따라 숫자가 다르게 보일 수 있다.
- **로그인 화면의 데모 계정으로 역할을 바꿔 보면 LNB 메뉴가 실제로 달라진다.** 이건
  버그가 아니라 §4의 RBAC 구조가 실제로 동작하는 것을 보여주는 것이다 — 화면 리뷰할
  때 Viewer 로도 한 번 들어가 보는 것을 권한다("메뉴가 왜 이거밖에 없지"가 아니라
  "이 역할엔 원래 이만큼만 보여야 하는가"를 확인하는 용도).
- **임시 외부 공개 터널 링크는 리뷰 기간에만 열려 있다.** 상시 접근 가능한 URL이
  아니므로, 팀 리뷰 일정과 어긋나면 링크가 닫혀 있을 수 있다.
- **화면 안의 문구(라벨·안내 문장)는 지금도 계속 바뀌는 중이다.** 이 문서는 화면이
  "무엇을 하는지"를 적었지, 화면 안 문구를 그대로 인용하지 않았다 — 문구 자체는
  `frontend/src/routes/*` 작업이 진행형이라 이 문서보다 화면이 항상 최신이다.
