# 화면 공통 규칙 — 어디에 뜨는가 · 어떻게 알리는가

> HMG 통합 포털(ICDAP·IDMS) 화면 규약. **새 화면을 만들기 전에 이 문서를 먼저 읽는다.**
> 여기 없는 상황을 만나면 **규칙을 먼저 정해 이 문서에 적은 뒤** 만든다 — 화면이 먼저
> 나가면 그게 그대로 규칙이 된다.
>
> 출처: 사내 Acrofuture Portal 프로젝트의 화면 규약을 이식했다. 그쪽 규칙 대부분이
> **실제 사고를 겪고 나서** 생긴 것이라(각 절의 ⚠ 표시), 같은 사고를 반복하지 않기 위해
> 근거째 가져왔다. 시각 토큰(색·글자·간격)의 정본은 `frontend/DESIGN.md` 다.

## 0. 왜 미리 정하나

화면마다 그때그때 정하면 같은 성격의 기능이 어떤 건 본문에서, 어떤 건 모달에서 열린다.
그러면 사용자는 누를 때마다 무엇이 일어날지 모른 채 누르게 되고, 그때부터 화면을 탐색이
아니라 **시도**로 쓴다. 규칙이 있으면 처음 보는 메뉴도 결과를 예측할 수 있다.

**한 줄로: 예측 가능성이 기능보다 앞선다.** ("예쁜 UI보다 사용자 중심 UX" — 고객 요구의 화면 판)

이 프로젝트에 특히 중요한 이유: 담당자가 디자인에 민감하고(컨텍스트 §6), 화면 수가
많아질 예정이다(KPI 대시보드 + 사양 관리 + 검증 + 결재 + 관리자). 규칙 없이 화면이
늘면 되돌리는 비용이 화면 수에 비례해 커진다.

## 1. 표시 영역 네 가지

가르는 기준은 둘뿐이다 — **얼마나 머무는가**, **본문과 함께 봐야 하는가.**

```
                  머무는 시간
                  짧다 ──────────────────────▶ 길다
   본문과   따로   │  MODAL          │  MAIN
   함께     ───────┼─────────────────┼──────────────
   봐야     같이   │  BOTTOM         │  RIGHT
   하나?           │  (흐르는 것)     │  (대조하는 것)
```

| | 목적 | 데스크탑 | 모바일(≤720px) | 이 프로젝트의 예 |
|---|---|---|---|---|
| **MAIN** | 그 자체가 일하는 화면 | 본문 | 본문 (그대로) | 사양서 목록 · KPI 대시보드 · 검증 결과 |
| **RIGHT** | 본문과 **대조**하며 본다 | 우측에서 **덮는** 패널 | **전체를 덮는 시트** | 사양서 상세(목록을 훑으며 본다) · 버전 이력 |
| **BOTTOM** | **흐르는 것**. 봤다가 접는다 | 하단 콘솔 | 하단 시트 60vh | 검증 실행 로그 · 배치 진행 로그 |
| **MODAL** | **끝내고 닫는 것** | 가운데 모달 | **아래에서 올라오는 시트** | 승인 요청 확인 · 사양서 등록 · 개인 설정 |

### 헷갈리는 자리 셋

- **RIGHT vs MODAL** — 본문을 가려도 되면 모달, 본문과 대조해야 하면 우측이다.
  버전 비교를 모달로 열면 "어느 사양서 얘기지?"를 확인하려고 매번 닫았다 열어야 한다.
- **BOTTOM vs RIGHT** — 시간순으로 흐르고 끝나면 안 볼 것은 아래(검증 로그), 목록을
  훑으며 본문과 맞춰 보는 것은 옆(버전 이력). 로그를 옆에 두면 가로가 좁아 줄이 다 접힌다.
- **MAIN vs MODAL** — 5초 안에 끝나면 모달, 그보다 길면 본문이다. 모달에서 오래 일하면
  뒤 화면이 궁금해지고, 그때 모달은 가리는 물건이 된다.

> ⚠ **RIGHT 는 덮는다. 밀어내지 않는다.** 격자에 열을 만들어 본문을 좁히면 열 때마다
> 본문이 출렁이고 읽던 줄이 접힌다 — 대조하려고 연 패널이 대조 대상을 흔든다.
> **가리개(scrim)는 두지 않는다** — 뒤가 읽혀야 대조다. 뒤를 가리는 것은 모달의 일이다.

> ⚠ **패널 위에 패널을 얹지 않는다.** 우측은 한 장이다. 목록→상세 짝이면 패널 **안을
> 2열**로 가르고(좁은 화면에서는 상세만 + [← 목록]), 일회성 확인·입력이면 모달로 얹는다.
> 여는 곳이 늘어나면 규칙만으로 안 지켜진다 — `clearRight()` 같은 관문 함수를 세워
> 새로 우측에 서는 화면이 그 관문을 지나게 한다.

> 결정(2026-08-05): **사양서 상세는 MAIN 본문 페이지다**(/specs/$specId) — 32개 필드
> 정의를 편집하는 "일하는 화면"이라 모달·드로어가 아니다. 그 안에서 **필드 하나의
> 편집만 RIGHT**(목록을 훑으며 한 필드에 집중 — 목록→상세 짝), 버전 비교·이력은
> **모달**(끝내고 닫는 것). 엑셀의 하단 시트는 화면에서 **카테고리 탭**으로 옮긴다.

### 모바일에서는 이름은 같고 모양만 바뀐다

**서버(또는 메뉴 정의)가 "무엇을 여는가"를 정하고, 화면이 "어떻게 여는가"를 정한다.**
이 경계를 지키면 모바일 대응이 서버를 건드리지 않는다.

모달을 모바일에서 가운데 띄우면 좁은 폭에서 여백만 먹고, 닫기 버튼이 위쪽 구석이라
한 손으로 못 닿는다. **아래에서 올리면 닫기가 엄지 자리에 온다.**

### 강제 장치 — 자리는 한 곳에서 정한다

표시 영역을 화면마다 스스로 정하게 두면 언젠가 어긋난다(원 프로젝트에서 서버가 MAIN
이라고 준 화면이 폭 96% 모달로 뜬 실사고). **그리는 곳을 한 곳으로 모은다** — 공통
`Surface`(또는 `Modal`/`Panel`/`Sheet` 관문 컴포넌트)를 지나야 화면에 뜬다.
`size="full"` 같은 옵션이 필요해지면 그것은 신호다 — **폭 96%를 덮어야 할 만큼 큰 것은
모달이 아니라 화면이다.**

메뉴가 동적 등록되는 이 플랫폼(컨텍스트 §2 메뉴 관리)에서는 **메뉴 정의에 surface 를
싣는 것**이 자연스럽다 — 프런트가 자리를 스스로 정하지 않는다.

## 2. 알림 네 가지

**사라지는 알림에 중요한 것을 담지 않는다.** 이것이 규칙 전체의 뼈대다.

| | 언제 | 사라지나 | 모바일 |
|---|---|---|---|
| **토스트** | 성공·완료 | 3~4초 뒤 | **하단** (상단은 주소창에 가리고 엄지에서 멀다) |
| **인라인** | 입력값 문제 | 고칠 때까지 | 그 칸 바로 아래 |
| **배너** | 화면 전체에 걸린 상태 | 원인이 사라질 때까지 | 헤더 아래 폭 전체 |
| **확인 모달** | **되돌릴 수 없는 것** | 사람이 답할 때까지 | 하단 시트 |

### 규칙 다섯

1. **오류를 토스트로만 끝내지 않는다.** 사라지고 나면 무엇이 잘못됐는지 알 길이 없다.
2. **입력 오류는 반드시 인라인.** 어느 칸이 틀렸는지 보여야 한다 — 칸이 열 개면 열 번 시도한다.
3. **확인 모달은 되돌릴 수 없는 것에만.** 삭제·승인·반려·배포. 남발하면 사람이 안 읽고
   누르게 되고, 정말 위험한 순간에도 안 읽는다.
4. **되돌릴 수 있으면 묻지 말고 되돌릴 길을 준다.** `"완료 처리했습니다 [실행 취소]"` 가
   `"완료하시겠습니까?"` 보다 낫다 — 앞은 한 번, 뒤는 매번 묻는다.
5. **문구는 세 가지를 담는다** — 무엇이 · 왜 · **다음에 무엇을.**
   `"저장 실패"` (X) → `"저장하지 못했습니다. 네트워크를 확인하고 다시 눌러 주세요."` (O)

### 고르는 흐름

```
되돌릴 수 없나? ──예──▶ 확인 모달 (그리고 무엇이 사라지는지 문장으로)
      │아니오
사용자가 방금 한 일의 결과인가? ──예──▶ 성공: 토스트(+되돌리기) / 실패: 인라인
      │아니오
특정 입력 때문인가? ──예──▶ 인라인
      │아니오
      └──▶ 배너 (연결 끊김 · 권한 없음 · 설정 필요)
```

### 겹침·모임

- 같은 메시지가 연달아 오면 하나로 묶는다(`외 N건`). 토스트는 한 번에 최대 3개.
- 배너와 토스트가 같은 원인이면 배너만.
- **알림이 모이는 자리는 종(🔔) 하나다.** 결재 대기·검증 실패·멘션이 각각 다른 자리에
  쌓이면 사람은 둘 다 습관적으로 안 본다. 배지 숫자는 *안 본 것*, 목록은 *안 끝난 것* —
  둘은 다르다. 알림 **설정**은 목록에 두지 않는다(목록은 지금 처리할 것).
- **일하는 중에 오는 것은 자리를 뺏지 않는다.** 긴 입력 화면에서 결재 요청이 와도 화면이
  바뀌지 않는다 — 종 배지(+급한 것만 얇은 띠)로 오고, 누르면 그때 패널이 덮는다.
  모달로 띄우지 않는다(입력하다 반사적으로 Esc 누른 사람이 무엇을 놓쳤는지 모른다).

### 긴 입력은 자리를 옮겨도 안 잃는다

성격이 다르면 처방도 다르다:

| | 새로 쓰는 것 | 이미 있는 것을 고치는 것 |
|---|---|---|
| 예 | 사양서 신규 요청 기안 | 사양서 수정 · Rule 편집 |
| 서버에 | 아무것도 없다 | 마지막 저장본이 있다 |
| 처방 | **초안을 붙든다**(draft) | **나갈 때 알린다**(이탈 경고) |
| 왜 | 잃으면 처음부터 | 초안을 따로 두면 "서버 값 vs 내 초안" 중 어느 쪽이 옳은지 답이 없다 |

초안 규칙 셋 — ①**묻는다, 덮지 않는다**(`[이어서 쓰기]`/`[새로 쓰기]`) ②언제 쓴 것인지
함께 적는다 ③**올라간 뒤에 지운다**(먼저 지우면 실패 시 통째로 사라진다). 파일 첨부는
안 붙든다. **깨끗하면 아무것도 안 묻는다** — 안 고쳤는데 물으면 사람은 안 읽고 누른다.

## 3. 기다림을 어떻게 보여 주는가

**이 제품은 기다림이 많다.** 검증엔진 배치(일 10만 건+), 엑셀 대량 업로드/마이그레이션,
수십만 건 다운로드, Tableau 로딩. 기다림을 안 보여 주면 사람은 **고장으로 읽고 다시
누른다** — 그리고 다시 누르면 대개 더 느려진다.

| | 언제 | 어디에 |
|---|---|---|
| **스켈레톤** | 목록·카드가 곧 채워질 때 | 그 카드 자리 |
| **버튼 안 로딩** | 사용자가 방금 누른 것 | 누른 그 버튼 |
| **영역 로딩** | 화면 한 구역이 통째로 바뀔 때 | 그 구역 안 |
| **진행 표시** | 10초 넘게 걸리는 것 | 단계·경과와 함께 |
| **진행 중 배너** | 그 일을 시작한 화면을 떠났을 때 | 화면 아래(모바일은 엄지 자리) |

### 규칙 여섯

1. 0.3초 안에 끝나는 것에는 아무것도 안 띄운다 — 깜빡임이 기다림보다 성가시다.
2. **누른 자리에서 알린다.** 버튼을 눌렀으면 그 버튼이 변한다.
3. **두 번 눌리지 않게 막는다**(`disabled`). 승인·배포처럼 되돌릴 수 없는 것은 특히.
4. **오래 걸리는 것은 무엇을 하는 중인지 말한다.** `2/4 단계 · 3분 경과` — 스피너만 돌면
   멈춘 것과 구별되지 않는다.
5. **실패하면 로딩을 지우고 이유를 남긴다.** 영원히 도는 스켈레톤이 제일 나쁘다 —
   기다리면 나올 것처럼 보이기 때문이다.
6. **떠나도 진행은 보인다.** 화면을 벗어나면 아래 배너로 남긴다 — 진행이 사라지면
   사람은 실행 자체를 못 믿고 같은 것을 또 누른다.

### 중복 요청을 막는 세 겹

```
① 화면   누른 버튼을 즉시 잠근다 — 두 번째 클릭이 아예 안 간다
② 요청   같은 요청이 떠 있으면 새로 안 보낸다
③ 서버   같은 일을 한 번만 만든다 (유니크 키 · 멱등)
```

**서버까지 가야 진짜로 막힌다.** ①②는 한 브라우저 안의 약속이라 탭 두 개면 뚫린다.
되돌릴 수 없는 동작(승인·배포·업로드 확정)에는 반드시 ③이 있어야 한다.

### 못 불러온 것과 없는 것은 다르다

```
빈 목록        "등록된 사양서가 없습니다"      ← 정말 없다
못 불러옴      "불러오지 못했습니다 …"         ← 다시 시도할 수 있다
계속 스켈레톤  (아무 말도 없다)                ← 금지. 사람이 영원히 기다린다
```

실패했는데 빈 목록을 보여 주면 사람은 할 일이 없다고 믿고 화면을 닫는다.
서버 판도 같다 — **집계 실패를 0으로 삼키지 않는다**(`catch → 빈 목록` 금지).

## 4. 다국어 — 이 프로젝트에서는 처음부터 지킨다

원 프로젝트에서는 "나중에 해도 되는 것"이었지만 **여기서는 요구사항이다**(IVI 다국어,
글로벌 조직). 지킬 것:

1. **사람마다 언어를 고른다** — 사용자 설정에 `locale` 칸. 조직 단위로 묶으면 그 사람만 못 바꾼다.
2. **서버는 문장이 아니라 재료를 준다.**
   ```
   좋음:  { status: "PENDING", statusLabel: "승인 대기" }
          { todayCount: 5, summary: "오늘 5건" }
   나쁨:  { status: "승인 대기" }     ← 영어를 붙이려면 서버부터 전부 뜯는다
   ```
3. **숫자가 낀 문구는 파라미터로** — `오늘 {n}건`. 영어는 복수형이 있어 문장 통째 저장은 사전이 성립하지 않는다.
4. 번역 대상이 **아닌 것**을 갈라 둔다 — 화면 문구·상태 이름은 번역하고, **사용자가 입력한
   값**(사양서 제목·태그·Rule 이름)과 **감사 로그로 남은 문장**(그때 일어난 일의 기록)은 안 한다.

## 5. 시각 위계 — 선·면·색을 각각 무엇에 쓰는가

화면이 어수선해 보이는 이유는 대개 요소가 많아서가 아니라 **구분 수단을 아무렇게나
섞어 써서**다. 셋을 각각 한 가지 일에만 쓴다.

```
선(border)   구역을 가른다        헤더 ↔ 본문 · 본문 ↔ 버튼 줄
면(배경)     "읽어야 하는 덩어리"  안내 · 경고 · 요약 숫자
색(글자)     상태를 말한다        승인=초록 · 반려=빨강 · 고른 것=흰 글자
```

하면 안 되는 것:
- 제목만 크게 하고 선을 안 긋는다 — 어디까지가 머리인지 몰라 본문이 붕 뜬다
- 경고를 글자색만 바꿔 문단에 섞는다 — 안 읽힌다. 면으로 띄우고 왼쪽에 색 띠를 둔다
- **상태를 배경색으로 칠한다** — 선택 강조 배경과 겹치는 순간 사람은 색을 안 믿는다.
  상태는 글자색(틴트 배지), 강조는 배경 (DESIGN.md 의 소프트 틴트 배지 규칙과 같다)

### 상태 칩과 이름표를 가른다

**점이 있으면 상태, 없으면 이름표.** 상태 칩(`● 배포 완료`)은 뜻이 색을 정하고
(부르는 쪽이 색을 안 고른다), 이름표(`#배터리`)는 테두리만·색 없음. 무슨 상태여도
같은 색이면 상태 칸을 봐도 정보가 없고, 이름표가 상태처럼 생기면 뜻 없는 글자가
상태로 읽힌다 — 둘 다 손해다. **모르는 상태는 회색으로 둔다**(뜻이 정해지기 전에는
아무 말도 안 하는 편이 낫다).

## 6. 치수 — 크기·간격·색은 토큰에서만 고른다

정본은 `frontend/DESIGN.md`(Tailwind `@theme` 토큰). 규칙 없이 매번 눈대중으로 정한
값은 하나하나는 그럴듯한데 모아 놓으면 리듬이 없다 — 그게 "촌스럽다"의 정체다.
(원 프로젝트 실측: font-size 411개 중 토큰 사용 17%, 손으로 박은 값 36가지 — 패널
제목이 본문보다 작아지는 위계 역전까지 갔다.)

- 글자·간격·모서리·그림자·색 전부 **토큰에서만**. 사이 값이 필요해 보이면 단계가 틀린 것이다.
- **숫자에는 `tabular-nums`** — 금액·건수가 갱신될 때 자리가 흔들리면 안 읽힌다.
- **`:focus-visible` 없이 `:hover` 만 주지 않는다** — 키보드 사용자에게는 아무 표시도 없는 화면이 된다.
- ⚠ **이름만 올린 글꼴은 없는 글꼴이다.** `font-family` 에 올린 글꼴은 반드시 번들로
  싣는다. 안 실으면 설치한 PC에서만 살고 나머지 전원은 맑은 고딕을 본다 —
  **이 저장소에서 이미 실제로 겪었다**(Pretendard, 2026-08-05 수정).
- 모노스페이스도 토큰에서만. 코드·경로·ID·버전(`SP-001`, `v2.3`)에만 쓰고 **한글 문장에는 안 쓴다.**
- ⚠ **같은 클래스 이름을 두 화면이 나눠 쓰지 않는다.** CSS는 나중에 선언한 쪽이 이긴다 —
  화면 코드에 잘못이 없는데 다른 화면이 깨지는 종류라, 그 파일만 봐서는 절대 못 찾는다.
  이름은 그 화면 것으로 짓고, 여러 화면이 함께 쓸 것은 한 번만 정의한다.
- 브라우저 기본 위젯도 앱의 물건처럼 입힌다 — `<select>`·`input[type="file"]` 기본
  모양이 남으면 그 줄만 딴 앱이다.

### 본문 페이지의 치수

기준 없이 화면마다 자기 값을 정하면 나란히 놓았을 때 다른 앱처럼 보인다. 페이지
여백·본문 최대폭·기본 글자 크기를 **`.page` 한 벌**로 묶고 전 화면이 물려받는다.
가로 여백은 `clamp()`(고정값이면 좁은 화면에서 내용이 여백에 먹힌다), 내용은 한
폭에서 멈춰 가운데 선다(긴 줄 끝에서 다음 줄 시작을 못 찾는다).

⚠ **모달·패널에서 본문으로 화면을 옮길 때** 모달 body 가 걸어 주던 패딩·간격이 통째로
사라진다 — 옮긴 뒤 반드시 눈으로 본다.

## 7. 패널·모달의 해부 — 머리·몸·발

```
┌──────────────────────────────┐
│ 머리  제목 · 닫기            │  면(배경)으로 가른다 + 아래 선. 안 스크롤된다
├──────────────────────────────┤
│ 몸    내용                   │  여기만 스크롤된다
├──────────────────────────────┤
│ 발    저장 · 취소            │  위 선. 붙박이 — 몸에 두면 밀려서 사라진다
└──────────────────────────────┘
```

- 제목은 그 표면에서 **가장 큰 글자**. 머리를 선 하나로만 가르면 스크롤하다 내용
  첫 줄처럼 읽힌다.
- 발의 주 동작은 오른쪽 끝(엄지 자리), 취소는 그 왼쪽.
- **막다른 길은 발이 아니라 막힌 그 줄에서 푼다.** 고르다 "값이 없네" 하는 사람의 눈은
  그 줄에 있다 — 두 곳 다 두는 것은 중복이 아니라 다른 순간이다.

### 닫기와 Esc

- 오른쪽 위 `×` 하나. 모든 표면에서 같은 모습(36×36 이상).
- **덮은 것은 전부 Esc 로 닫힌다** — 모달만 되고 패널은 안 되면 사람은 마우스만 쓴다.
- 닫는 순서는 **위에 덮인 것부터 하나씩.** 한 번에 다 닫으면 읽던 것까지 잃는다.
- **MODAL 만 배경막을 눌러 닫는다.** RIGHT·BOTTOM 은 배경막이 없다(뒤를 보는 것이 목적).
- 저장 안 한 값이 있으면 배경막·Esc 로 안 닫는다 — 먼저 묻는다(§2 확인 모달 규칙).

### 스크롤은 덮은 것 안에서 끝난다

브라우저 기본값은 안쪽 스크롤이 끝에 닿으면 바깥으로 넘긴다 — 모달을 끝까지 내리면
뒤 본문이 따라 구르고, 닫았을 때 읽던 자리가 사라진다. **둘이 한 쌍이다:**

```
overscroll-behavior: contain   구르는 자리 안에서 끝낸다
body scroll lock               덮여 있는 동안 뒤 화면 자체를 잠근다
```

넓은 화면의 RIGHT 패널만 예외로 안 잠근다(본문과 대조가 목적). 덮은 것 안에 새 스크롤
영역을 만들면 contain 목록에 같이 더한다 — 빠뜨려도 안 터지고 "가끔 뒤가 움직인다"로만 나타난다.

### ⚠ 높이는 `100vh` 가 아니라 `100dvh`

iOS Safari 의 `100vh` 는 주소창이 숨겨졌을 때의 높이다. 하단 고정 요소가 도구막대 뒤로
들어간다. `height: calc(100vh - …)` 줄을 남기고 그 아래 `100dvh` 판을 겹쳐 쓴다.
**데스크톱 크롬에서도, Playwright 모바일 뷰포트에서도 재현되지 않는다** — 이 부류는
실제 기기에서만 확인된다. 판이 초록이라고 iOS 가 괜찮다는 뜻이 아니다.

## 8. 모바일 — 처음부터 함께 만든다

**방침(원 프로젝트에서 합의된 것을 그대로 채택):**

```
접는 구조(레이아웃)        화면 만들 때 같이 — 나중에 하면 다시 짜게 된다
가로 스크롤·넘침           모바일 스모크 e2e 가 393px 에서 자동으로 잡는다
터치 타깃·스크롤 감(마감)  화면이 다 올라온 뒤 모바일 전용 세션에서 사람이 본다
```

### 손가락 크기 — 좁은 화면에서만 조작을 키운다

원 프로젝트 393px 실측: 조작 대부분이 21~31px — 마우스로는 되지만 손가락으로는 옆 것이 눌린다.

```
조작 최소       높이 40px (표 안·칩 안은 36px 로 타협)
아이콘 버튼      폭도 36px — 높이만 키우면 폭이 13px 로 남는다
체크박스         24px
입력 글자        16px 이상 — 그 아래면 iOS 가 화면을 확대해 버린다
input           min-height 40px — 글자만 키우면 여전히 못 누른다 (실측된 구멍)
```

⚠ **넓은 화면은 그대로 둔다** — 데스크톱에서 44px 로 키우면 목록이 반으로 줄어든다.
밀도는 마우스의 이점이다. ⚠ **`min-height` 로만 키운다** — `height` 로 박으면 두 줄
항목이 잘린다.

### 좌측 메뉴(서랍) — 고르면 닫힌다

```
넓은 화면   [내비][본문]    나란히 — 그대로 둔다
좁은 화면   [내비 ▓▓▓▓]    본문을 덮는다 — 잎(메뉴 항목)을 고르면 닫는다.
                            가지(섹션 펼침)는 그대로 둔다 — 닫으면 다음에 누를 것이 사라진다
```

⚠ 골라도 서랍이 남아 있으면 **방금 연 것을 가린다**(실측: 264px 서랍+가림막이 남아
그 뒤가 눌리지도 않았다).

### 그 밖의 좁은 화면 규칙

- **앱 헤더는 어떤 덮개도 먹지 않는다** — 헤더까지 덮으면 지금 어디인지와 나가는 길이
  동시에 사라져 사람이 브라우저 뒤로가기를 누른다(앱을 벗어난다).
- 표는 **자기 상자 안에서만 가로로 흐른다**(페이지는 안 밀린다). 오른쪽에 열이 더
  있으면 **가장자리 그림자**로 말한다 — 표시가 없으면 사람은 "열이 이것뿐"이라고 읽는다.
- z-index 는 **이름 붙인 사다리에서만** 고른다(`--z-nav < --z-panel < --z-fab <
  --z-backdrop < --z-modal < --z-dialog`). 화면마다 숫자를 손으로 적으면 하단 시트가
  떠 있는 버튼 뒤로 들어가는 날이 온다(실사고).
- **이름 칸**(띄어쓰기 없는 긴 글자 — 파일명·ID)은 넷을 다 갖춘다:
  `display:block; min-width:0; white-space:nowrap; overflow:hidden; text-overflow:ellipsis` —
  하나라도 빠지면 겹쳐 찍히거나·말줄임이 안 걸리거나·한 글자씩 세로로 선다(각각 실사고).
  그리고 줄이는 것과 읽히는 것은 다르다 — 옆 칸이 많으면 좁은 화면에서는 이름에 한 줄을 통째로 준다.
- 표면 사이 이동에서 **덮개는 쌓지 않는다** — MODAL→MODAL 은 앞 모달을 걷고,
  RIGHT→MODAL 만 위에 서고 닫으면 패널로 돌아온다. 예외는 확인 창 하나(답이 둘뿐이고
  즉시 사라진다).
- 켜 둔 화면에는 새 판이 저절로 안 온다 — 배포 후 `/api/version` 을 주기 확인해
  **알리기만** 한다(저절로 새로고침하면 쓰다 만 것이 날아간다. [나중에]를 누르면 그
  판에서는 다시 안 묻는다).

## 9. 목록·표 — 길어지면 못 읽는다

이 프로젝트는 표가 본체다(사양 목록·검증 결과·KPI 표·이력). **표는 한 곳에서만
그린다** — 공통 `DataTable` 관문. 화면은 열 정의와 줄 데이터만 주고, 머리 고정·정렬·
검색·페이징·빈 상태·모바일 가로 스크롤은 전부 안에 있다.

⚠ 원 프로젝트의 경고: "DataTable 로 이관했다"고 **문서에 손으로 적은 상태는 코드와
어긋난다** — 이관 표는 매번 `grep` 으로 다시 세서 적는다. 그리고 트리처럼 성격이 다른
것을 억지로 관문에 넣으면 관문에 화면별 예외가 붙어 "한 곳에서만 그린다"가 이름만
남는다 — **관문을 먼저 키우고 옮긴다.**

### 몇 건부터 접나

```
 ~20줄    그냥 다 보여 준다        스크롤 한 번에 훑힌다
 21줄~    페이징(20줄씩)           "더 보기"가 아니라 페이지 — 몇 번째를 보는지 알아야 한다
 31줄~    + 검색칸 기본            이름으로 좁히는 게 가장 빠르다
 축이 있으면 + 칩 필터             차종·국가·상태처럼 값이 몇 개뿐인 축
```

### 지키는 것

- **숫자 열은 오른쪽 정렬 + `tabular-nums`.** 끝을 맞춰야 눈이 자릿수를 센다. 머리글도 그 열을 따른다.
- 정렬 기본값은 서버가 정한다(시간 축은 시간순, 금액 축은 큰 것부터). 사람이 바꾼 정렬은 기억하지 않는다.
- 머리줄은 배경으로 갈리고 고정된다.
- 빈 값은 `—` 로 적는다 — 빈 칸이 이어지면 표가 깨진 것처럼 보인다.
- 빈 상태는 "없다"와 "못 불러왔다"를 가른다(§3).
- 줄을 누르면 무엇이 열리는지 예측 가능해야 한다 — 누를 수 있으면 커서와 호버로 말한다.
- 편집 표의 `render(row, index)` 에서 index 는 **원본 rows 안의 자리**다(보이는 자리가
  아니다 — 걸러진 뒤의 자리를 주면 엉뚱한 줄이 고쳐진다). 편집 중에는 검색을 끈다
  (고치는 도중 줄이 걸러져 사라지면 어디까지 고쳤는지 잃는다).
- 합계는 마지막 줄로 끼우지 않고 `tfoot` 으로 따로 세운다 — 검색·페이징에 휩쓸리면
  2쪽에서 사라지고, 검색하면 합계만 남는다.
- **같은 목록을 한 화면이 두 군데서 각자 불러오지 않는다** — 언젠가 갈라지고, 갈라진
  순간 어느 쪽을 믿을지 모른다. 바뀌었다는 신호 하나를 위에서 들고 내려보낸다.

## 10. 숫자를 보여 주는 화면 (KPI 대시보드 · 검증 통계)

ICDAP 이 통째로 이 종류다. **새 지표 화면은 이 절을 먼저 본다.**

- **넣는 곳과 보는 곳을 가른다.** 같은 편집 화면을 두 곳에 만들지 않는다 — 보는 화면에는
  넣는 화면으로 **가는 길**만 둔다(권한 있는 사람에게만).
- **카드는 다음 행동으로 끝난다.** 숫자만 보여 주고 끝내면 "그래서 어디서 보나"를 사람이 찾는다.
- **숫자는 전과 견준다.** `달성률 82%` 만으로는 좋은지 나쁜지 모른다 — 큰 숫자 옆에
  전기 대비 증감(`▲12%`). 앞 기간이 0이면 아무 말도 하지 않는다(`+∞%` 를 적는 순간
  사람은 그 숫자를 안 믿는다). 색만으로 말하지 않는다 — 화살표와 숫자가 함께 간다.
  좋은 방향은 지표마다 다르다(달성률은 오르면 좋고 오류율은 내리면 좋다).
- **예상과 확정을 갈라 적는다.** 한 표에 섞이면 전부 확정으로 읽혀 예상치가 회의에서
  사실처럼 인용된다. 알약 하나로 가른다 — `확정`/`예상`.
- **0을 평온함으로 읽지 않는다.** 자료가 없어 못 세는 것과 정말 없는 것을 가른다.
  ⚠ **빈칸을 0으로 세면 그 화면은 조용히 거짓말을 한다** — 저장은 nullable, 계산은
  한 칸이라도 비면 결과를 안 내고, 화면은 무엇이 비었는지 이름을 적는다.
- **같은 이름의 숫자는 한 곳에서 센다.** 화면마다 '달성률'의 셈법이 다르면 사람은 둘 다
  안 믿는다. 일부러 다르게 세면 이름에 그 차이를 적는다(`달성률(분기 기준)`).
- 넣는 값과 읽는 값을 함께 보여 준다 — `47952381` 은 4,795만인지 4억인지 눈으로 못 센다.
- 표를 채우는 화면은 **즉시 저장**(칸을 벗어날 때). [저장] 버튼을 두면 스무 칸을 고치고
  안 누른 채 나간다. 실패하면 서버 값으로 되돌린다.
- 권한 범위로 잘라 준 숫자(내 팀/센터/전사)는 **어디까지의 숫자인지**를 함께 싣는다 —
  라벨을 버리면 자기 팀만 본 값을 전사 값으로 읽는다.

### 차트

- **시계열은 선, 구성비는 막대.** 형태를 먼저 고르고 색은 마지막에.
- 계열 색은 눈대중으로 고르지 않는다 — 색각(deutan/tritan) 분리도·명도대·대비를 검증기로
  통과한 값만(`dataviz` 스킬). 다크는 자동 반전이 아니라 그 배경에서 다시 통과시킨 값이다.
- **계열 색과 상태 색을 섞지 않는다** — 섞이면 "빨간 막대가 매출인지 위험인지" 알 수 없다.
- 계열이 둘 이상이면 범례는 늘 있고, 값은 마크 옆에 직접 적는다.

## 11. 종류가 칸을 정하는 화면 — 만들기 전에 종류를 고른다

한 화면이 성격이 다른 것 여러 개를 받으면(신규/수정/삭제 요청, 검증 Rule 유형 등),
폼 안의 셀렉트 하나로 칸이 나타나고 사라지게 두지 않는다 — 먼저 아무 종류로나 폼이
열리고, 사람은 반쯤 채운 뒤 종류를 바꾸며, 그 순간 방금 쓴 칸이 사라진다.

1. **고르는 것이 먼저다.** 종류에 따라 칸이 절반 이상 달라지면 카드로 먼저 고르게 한다.
   카드에는 이름만이 아니라 **무엇이 달라지는지**를 함께 적는다.
2. 저장된 뒤에는 종류를 못 바꾼다(값의 뜻이 바뀐다). 저장 전에는 [다시 고르기].
3. 안 쓰는 칸은 감추고, 칸 이름도 종류에 맞게 쓴다.
4. 판단은 한 곳에(서버/데이터 정의) — 화면은 그린다.

## 12. 메뉴·화면 이름 짓기

이름 = **누구 것(층위) + 무엇.** 같은 '관리'인데 하나는 내 것이고 하나는 시스템 것이면
눌러 보기 전에는 무엇이 열릴지 모른다.

```
 내 것        마이페이지 · 개인 설정        내 정보 · 내 알림 · 내 언어
 서비스 것    사양서 관리 · KPI 관리        그 서비스의 업무 화면
 시스템 것    시스템 관리                   메뉴·권한·사용자 (Admin 이상)
```

- 정본은 메뉴 정의(서버) 하나 — 모달 제목·검색 팔레트·e2e 가 같은 낱말을 쓴다. 이름을
  바꿀 때는 grep 으로 하드코딩된 사용처까지 한 번에 바꾼다(반쯤 바꾸면 메뉴에서는 A 인데
  열린 창 제목이 B).
- 아이콘은 **뜻마다 하나씩**, 정본 파일 한 곳(`lib/icons`)에서만 — 같은 그림이 두 뜻이면
  사람은 잘못 읽고 눌러 본 뒤에야 안다. 그림문자(이모지) 대신 **선 아이콘**(currentColor·
  1em)을 쓴다 — 그림문자는 기기·글꼴마다 다르게 그려지고 색을 못 물려받는다.
  그림을 label 글자에 섞지 않는다(검색이 그 글자까지 훑는다).

## 13. 탭·단축키 — 관문에 모은다

- **탭 활성 표시를 손으로 쓰지 않는다.** 공통 `Tabs` 컴포넌트 — 부르는 쪽은 값 하나만
  준다. 활성 클래스가 화면마다 갈리면(`active` vs `on`) 틀리게 써도 아무 일도 안
  일어나고, 그냥 **아무 탭도 안 켜진 화면**이 된다. `role="tablist"`·`aria-selected`·
  화살표 이동은 관문이 지킨다. 개수 배지는 `tabular-nums`(1↔2자리에서 폭이 안 튄다).
- 단축키를 도입하면: 정본 목록 한 곳(도움말도 거기서 그린다 — 손으로 적은 도움말은
  반드시 어긋난다) · 입력 중에는 아무 키도 안 가로챈다 · **되돌릴 수 없는 동작
  (삭제·승인·배포)에는 안 건다** · 권한 없는 화면은 단축키·팔레트로도 안 열린다
  (권한을 메뉴에서만 걸면 팔레트가 뒷문이 된다).

## 14. 이 문서를 지키는 방법

| | |
|---|---|
| 표시 영역 | 메뉴 정의가 정하고, 그리는 곳은 공통 관문 한 곳 |
| 알림 | 공통 컴포넌트로만 — 화면마다 `alert()`·직접 만든 배너 금지 |
| 표 | `DataTable` 관문 하나 — 이관 상태는 grep 으로 세서 적는다 |
| 탭·칩·아이콘 | 각각 정본 한 곳 |
| 치수·색 | `frontend/DESIGN.md` 토큰에서만 |
| 모바일 | 접는 구조는 화면과 같이 · 모바일 스모크 e2e(393px)가 가로 스크롤·넘침을 매번 잡는다 |
| 마감 | 화면이 다 올라온 뒤 모바일만 훑는 세션에서 사람이 본다 |

**문서·타입·상수에만 적힌 판단은 반드시 어긋난다** — 판단은 한 곳(관문 컴포넌트·순수
함수)에서 하고 그 한 곳을 지나가게 강제한다. 규칙을 문서에만 적어 두면 화면마다 자기
자리를 스스로 정한다(원 프로젝트에서 반복 실증된 병이다).

새 절을 더할 때는 지금 있는 마지막 절 번호를 먼저 확인한다 — 번호는 코드 주석·커밋이
가리키는 주소라 나중에 바꾸면 참조가 전부 어긋난다.

## 15. 이름이 어긋나면 **있는 것도 없는 것이 된다** (2026-08-05 · acrofuture 실증)

12절이 이름 **짓는 법**을 정한다면, 이 절은 이름이 어긋났을 때 **무슨 일이 벌어지는가**다.
자매 프로젝트(acrofuture)에서 하루에 같은 병으로 세 번 걸렸다. 셋 다 **기능은 멀쩡했고
이름·색만 어긋나 있었다.**

```
"회사 사용자 관리가 안 보임"    → 있었다. 제목이 '멤버' 하나뿐이라 눈에 안 걸렸다
"이 기능은 저쪽으로 가야         → 맞게 놓여 있었다. 다른 층의 같은 기능과 제목이 같아
  하는 것 아닌가"                   잘못 놓인 것처럼 보였다
"고른 게 안 보임"                → 골라져 있었다. 카드와 배경이 같은 색이었다
```

- **사람이 쓰는 낱말로 짓는다.** 화면을 찾는 사람은 자기 머릿속 낱말로 찾지, 우리가
  정한 이름으로 찾지 않는다.
- **같은 이름을 두 곳에 두지 않는다.** 층이 다르면 **이름에 층을 넣는다** — 부제의
  작은 글씨로만 가르면 "왜 여기 또 있지"가 된다.
- **층이 겹치면 어느 쪽이 이기는지 그 자리에 적는다.** 우선순위를 적어 두지 않으면
  아래층에 넣고도 왜 안 먹는지 알 길이 없다.
- **여기서 되는 일과 저기서 하는 일을 갈라 적는다.** 없는 기능을 찾아 헤매는 것을 막는다.

## 16. 고른 것은 **면으로** 말한다 (2026-08-05)

- 카드 배경과 그 카드가 놓이는 판의 배경이 **같은 색이면 카드가 아니라 배경이다.**
  카드는 한 단 띄운다.
- 선택 표시를 얇은 테두리 하나로 두지 않는다. **색 면 + 굵은 테두리** 두 겹으로 준다.
- **글자로도 남긴다**(`✓ 선택됨`). 색만으로 구분하면 색을 못 가르는 사람에게는
  표시가 없는 것과 같다(5절 시각 위계의 실전판).

## 17. 빈 자리에 **이유를 적는다** (2026-08-05)

아무것도 없는 칸은 **"아직 없음"과 "고장"과 "안 불러옴"을 구별해 주지 않는다.**

- 만들 수 있는 사람에게는 만드는 버튼이 보이니 그럭저럭 읽힌다. 문제는 **만들 권한이
  없는 사람**이다 — 그 사람에게 그 칸은 영원히 비어 있다.
- 그래서 **권한에 따라 다르게 적는다.** 만들 수 있으면 "만들면 이렇게 됩니다",
  없으면 "누구에게 요청하세요".

## 18. 한 화면에 **열네 칸을 쌓지 않는다** (2026-08-05)

관리 화면이 한 줄로 늘어서면, 아래쪽 기능은 **있는데도 없는 것과 같다**(15절과 같은 병).

- **성격으로 가른다.** 대상 자체 · 사람 · 운영(키·연동·기준) · 지나간 기록.
- **관리 행위와 결과 보기를 나눈다.** 감사 로그·사용량은 무엇을 바꾸러 온 자리가
  아니라 무엇이 바뀌었는지 보러 온 자리다 — 오는 사람이 다르다.
- **기본 탭은 가장 자주 오는 이유로 연다.**
- 탭이 넷을 넘으면 좁은 화면에서 눌린다 → 8절(가로 스크롤로 밀리게 둔다).

## 19. 만든 것을 **알린다** (2026-08-05)

**만들어 놓고 아무도 모르는 기능은 없는 것과 같다.** 배포해도 그 사실이 화면 어디에도
남지 않으면, 쓰는 사람은 우연히 눌러 보기 전까지 모른다.

```
whatsnew 정본   새 기능 한 줄 — 날짜 · 무엇이 달라졌는지 · 갈 곳
가이드의 '새 기능' 탭   목록으로 본다
메뉴의 N 배지    목록까지 안 가도 눈에 걸린다(한 번 열면 내려간다)
```

- **기능을 배포하면 여기에 같이 적는다.** 안 적으면 또 아무도 모르는 기능이 된다.
- **갈 곳이 있으면 버튼을 준다.** "생겼대요"만 알려 주고 어디 있는지 안 알려 주면
  안내가 아니다.
- 배지는 **가장 최근 날짜 하나로** 센다. 항목마다 읽음 표시를 두면 "다 읽었는데 배지가
  남았다"가 생긴다 — 배지는 알림이지 체크리스트가 아니다.

## 20. 안내는 **한 장으로 펴고 시간을 말한다** (2026-08-05)

처음 사용 안내를 일곱 장으로 넘기게 했더니 사람이 중간에 닫았다. 끝이 몇 장 남았는지
점으로 보여 줘도 마찬가지다.

- **한 장으로 편다.** 한 번에 훑고 필요한 데서 멈추게 한다.
- **이름을 부른다** — 안내가 '나에게 하는 말'이 된다.
- **읽는 데 걸리는 시간을 먼저 말한다**("30초만"). 끝을 모르는 글은 첫 줄에서 닫힌다.
- **칸마다 [열어 보기]** 를 둔다. 넘기는 방식에서는 버튼이 아래 한 자리뿐이라 지금
  보고 있는 화면만 열 수 있다.
- 안내 아이콘은 **크게, 부드러운 색 원 위에**. 글자 옆의 작은 그림은 훑을 때 눈에 안
  걸리는데, 안내는 훑다가 걸려야 읽힌다.

## 21. 화면이 **자기 상태를 말한다** (2026-08-05)

- **로그인이 풀리면 화면이 알아채고 로그인으로 보낸다.** 401 을 그냥 오류로 흘리면
  화면마다 "요청에 실패했습니다 (401)" 만 뜨고, 사람은 다시 로그인해야 한다는 걸 알
  방법이 없다 — 화면은 멀쩡한데 아무것도 안 되니 "고장 났다"로 읽힌다. 로그인 화면은
  **왜 나왔는지** 말해 준다.
  ⚠ 로그인·가입 요청의 401 은 제외한다. 그건 "비밀번호가 틀렸다"는 뜻이라 그 자리에서
  보여 줘야 하고, 내보내면 입력이 날아간다.
- **연결 실패에 사람의 말을 준다.** `Failed to fetch` 를 그대로 올리면 사람이 할 수
  있는 일이 없다.
- **비워 두면 어떻게 되는지 그 자리에서 말한다.** 알림 주소를 비우면 앱 안에서만
  보인다는 것을 안 적으면 "켰는데 왜 안 오지"가 되고, 사람은 고장 난 줄 안다.
- **첫 조회를 폴링에 맡기지 않는다.** 주기 뒤에 처음 부르는 훅이라면 따로 한 번 불러야
  한다 — 안 그러면 주기만큼 빈 화면이고, **안 열리는 것과 늦게 열리는 것은 화면에서
  구별되지 않는다.**
- **쓰던 것이 있으면 창을 닫기 전에 묻는다.** 화면 이동은 초안 저장이 막아 주지만
  새로고침·닫기는 무방비다. ⚠ 쓴 것이 있을 때만 건다 — 늘 뜨는 경고는 곧 안 읽고
  누르게 되고, 그러면 정작 필요할 때도 그냥 눌러 버린다.
