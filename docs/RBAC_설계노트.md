# RBAC 설계 노트 — 본개발에서 지킬 것

> 2026-08-05. acrofuture 포털이 운영에서 실제로 겪은 사고와 그 해법을 HMG 포털에
> 맞게 옮긴 것이다. 프로토타입 화면에는 일부만 반영되어 있다(범위 축·자기 잠금·최소
> 메뉴·사람 말 힌트·내 권한·보유자 표시) — 나머지는 본개발에서 이 문서가 정본이다.

---

## 1. 권한 이름은 `동사.자원.범위` — 범위 축을 처음부터

```
spec.read.team        사양서 조회 — 우리 팀까지
deploy.approve.all    배포 승인 — 전체
```

- **화면에 들어갈 수 있는가와 무엇까지 보이는가는 다른 문제다.** 범위를 나중에 붙이면
  모든 조회 API 를 다시 손대야 한다.
- 범위는 `own < team < all` 이고 **넓은 것이 좁은 것을 자동 포함**한다(포함 판단은
  서버 한 곳). 화면에는 **가장 넓은 것 하나만** 보여 준다 — 넷을 다 적으면 사람은
  "권한이 넷"으로 읽는다.
- ⚠ 범위를 넘겨 부여하면 권한 이름이 거짓말이 된다 — `*.team` 권한을 회사 범위로
  배정하면 사실상 `.all` 이 된다. "팀 범위가 필요한 역할인가"는 **권한 이름에서
  파생**해 판단한다(별도 컬럼로 두면 언젠가 어긋난다).

## 2. 메뉴는 서버가 내려준다 — `GET /api/me/menu`

- 프런트는 **그리기만** 한다. 권한 판단이 두 곳이면 언젠가 어긋나고, 어긋난 쪽이
  대개 화면이라 사람이 먼저 당황한다.
- **보이는 것과 되는 것을 나눈다** — 메뉴·이력은 보이되 실행 버튼만 비활성.
  눌러서 "권한이 없습니다"가 뜨는 것은 나쁜 화면이다.
- **최소 메뉴**(`requires = null`)를 둔다 — 권한으로만 가리면 권한 적은 역할의
  LNB 가 텅 빈다. 공지·Q&A·FAQ·가이드가 여기 속하고, **가이드에는 권한을 걸지
  않는다**(권한 없는 사람일수록 "나는 무엇을 할 수 있나"가 궁금하다).
- 빈 섹션은 내려보내지 않는다 — 열었더니 아무것도 없는 것도 나쁜 화면이다.

## 3. 유령 권한을 만들지 않는다

acrofuture 실사고: **정의·시드·메뉴 라벨만 있고 실제 게이트(`require`)가 없는 권한이
6개** 있었다 — "있는 기능"으로 세어지는데 실제로는 아무 일도 막지 않는다.

- 권한 상수 목록 ↔ 실제 검사 지점의 정합을 **테스트로** 잡는다.
- 반대 방향도 본다: **API 만 있고 화면이 없는 기능**은 한 건도 쓰일 수 없는데
  "있는 기능"으로 세어진다.

## 4. 새 권한은 기존 역할에 자동으로 붙지 않는다

역할의 권한은 회사가 고칠 수 있으므로 시드는 **비어 있을 때만** 채운다(매번 덮으면
회사가 조정한 것을 기동 때마다 되돌린다). 그 결과 —

- 새 기능의 새 권한은 이미 운영 중인 회사의 **아무 역할에도 안 붙는다** → 메뉴가
  아무에게도 안 보인다 → 기능이 없는 것과 같다.
- 해법: **그 권한을 가진 역할이 하나도 없을 때만 관리자 역할에 1회** 얹는다
  (다른 역할에 이미 줬으면 건드리지 않는다 — 일부러 뺀 경우와 구별해야 하므로
  "새 권한"에 한정한다).

## 5. 자기 잠금 방지

관리자가 자기 역할에서 [권한 관리]를 빼는 순간 회사 안의 누구도 되돌릴 수 없다.
저장 전에 **그 권한을 가진 사람이 회사에 남는지 세어 보고, 0명이면 되돌린다**
(예외를 던지면 트랜잭션이 통째로 롤백되므로 반쯤 잠긴 상태가 없다).
플랫폼 관리자는 세지 않는다 — "고치려면 플랫폼 관리자를 부르세요"는 회사 입장에서
잠긴 것과 같다.

## 6. 역할 배정은 범위와 함께, 회수를 빠뜨리지 않는다

- "팀장"은 **어느 팀의** 팀장인지가 붙어야 뜻이 있다. 배정 한 줄 = (사람, 역할, 범위).
- 담당을 바꾸면 **앞 사람에게서 먼저 회수**한다 — 빠뜨리면 물러난 담당이 계속
  실행할 수 있고 아무도 모른다.
- 권한이 붙는 길은 여러 갈래고 전부 말없이 붙는다 → 받은 본인이 확인할
  **[내가 할 수 있는 것]** 화면을 둔다(권한 이름이 아니라 사람 말로).

## 7. 조직 층수를 코드에 박지 않는다

그룹 → 계열사 → 본부 → 팀 — 층수는 데이터다:

```
OrgUnit { id, parentId, kind: "계열사"|"본부"|"팀"…, name }   kind 는 이름표일 뿐
```

코드가 아는 것은 하나 — "이 사람이 배정된 노드와 그 아래 전부". 범위 판단은
**부르는 쪽이 하지 않는다**(호출처가 트리를 알아야 하면 한 곳만 빠뜨려도 "그 사람에게
그 화면만 안 열린다"가 된다). 순환·깊이는 트리 계산 한 곳에서 막는다.

## 8. 역할 수만큼 화면을 만들지 않는다

같은 화면 + **범위 선택기 하나**. 선택지는 권한이 정하고, 하나뿐이면 선택기가 아예
안 뜬다. 후보에 없는 값이 오면 거절 대신 **첫 후보로 되돌린다**(거절하면 권한이
좁아진 사람에게 화면이 통째로 안 열려 고장으로 보인다). 역할별로 다른 것은 홈
대시보드의 기본 배치 하나면 충분하다 — HMG 는 이미 역할 파생 프리셋으로 구현됨.

## 9. 권한은 사람 말로 보여 준다

체크박스에 `expense.approve.team` 이 그대로 뜨면 아무도 못 고른다.

- 권한마다 `label`(사람 말) + `hint`(**고르면 무엇이 열리는가**) + 묶음.
- 되돌리기 어렵거나 밖으로 나가는 액션(승인·삭제·다운로드)에는 ⚠ 를 붙인다 —
  "여기서 실제 배포가 나갑니다".
- 필드 수준 가림도 같은 원칙: 같은 화면에서 더 좁은 권한만 보는 값(예: 보안/감사
  카테고리 필드)은 **화면을 따로 만들지 말고 권한이 필드를 가린다**.
