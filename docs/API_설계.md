# API 설계 — 사양서 · 결재 · 배포 (FR-114 중심)

> **이 문서의 자리.** 프로토타입은 사양서·결재·배포를 **프런트 스토어**(`data/specStore.ts`,
> `approvalStore.ts`, `deployStore.ts`, 잇는 자리 `workflow.ts`)로 돌린다. 서버는 아직 안 붙였다
> (요구사항 OPN-003 '배포' 대상 정의 미확정 — 먼저 만들면 두 번 만든다).
> 다만 **화면을 만들며 알아낸 규칙**(상태 전이·회수 조건·결재선이 굳는 시점·반려 사유 필수)은
> 지금 적어 두지 않으면 본개발에서 다시 발굴 대상이 된다. 그래서 **서버는 안 만들고 모양만 굳힌다.**
>
> 이미 붙어 있는 것(`/api/me`·`/members`·`/audit`·커뮤니티 등)의 규약을 그대로 잇는다:
> - 응답은 **자원 그대로**(래핑 없음). 목록은 배열, 단건은 객체.
> - **권한이 없으면 403 이 아니라 빈 목록**이다 — "없는 것"과 "막힌 것"을 가른다
>   (`GET /api/specs` 주석 참고). 단건 조회는 404.
> - 규칙 위반은 **409**(자기 잠금 방지가 이미 그렇다), 입력 부족은 400.
> - 토큰은 `Authorization: Bearer <약식 세션>` — JWT 확정 시 관문만 교체.
> - 값(상태·종류)은 **한국어 정본 문자열**을 그대로 주고받는다. 화면이 사전으로 표시만 옮긴다.

## 1. 사양서 (Spec)

### 상태와 전이 — 화면이 이미 이렇게 돈다

```
초안 ──상신──→ 승인 대기 ──최종 승인──→ 승인 완료 ──배포 승인──→ 배포 완료
 ↑ │              │  │                        │
 │ └─검토 중 ─────┘  └─회수(판단 전만)───────→ │
 └────반려(사유 필수, 사유를 안고 돌아온다)────┘
```

- `승인 완료` 는 2026-08-18 에 늘린 상태다. **없으면 승인해도 화면이 안 바뀐다** — 승인은
  끝이 아니라 배포 앞의 자리다.
- **결재 중에는 본문을 고칠 수 없다**(승인자가 본 문서가 그대로 승인되어야 한다).
  서버도 같은 규칙을 지킨다: `승인 대기` 인 사양서의 필드 수정은 409.

### 엔드포인트

| 메서드 | 경로 | 뜻 |
| --- | --- | --- |
| GET | `/api/specs` | 목록(카탈로그). 권한 없으면 `[]` — 이미 있음, 필드까지 확장 |
| GET | `/api/specs/{id}` | 단건 + 현재 버전 + 이력 |
| POST | `/api/specs` | 등록 — v0.1 초안으로 태어난다 |
| PUT | `/api/specs/{id}/fields` | 필드 정의 일괄 저장 (⚠ `승인 대기` 면 409) |
| GET | `/api/specs/{id}/approvals` | 이 사양서의 결재 이력 (FR-114 ④) |

```jsonc
// GET /api/specs/{id}
{
  "id": "SP-001",
  "name": "VN7 엔진 사양서",
  "category": "파워트레인",
  "description": "…",
  "tags": ["엔진", "VN7"],
  "author": "김민준",
  "updated": "2026.07.15",
  "history": [
    {
      "version": "v2.3",
      "status": "승인 대기",          // 초안 | 검토 중 | 승인 대기 | 승인 완료 | 배포 완료
      "date": "2026.07.15",
      "summary": "최대 출력 상향",
      "author": "김민준",
      "fields": [{ "label": "최대 출력", "value": "290 hp @ 5,800 rpm" }],
      // 반려당한 자국 — 되돌아온 문서는 **이유를 안고 온다**(규약 §17)
      "rejection": { "reason": "시험성적서 누락", "by": "한동현", "at": "2026.08.18" }
    }
  ]
}
```

```jsonc
// POST /api/specs  { name, category, description, tags }
// → 201, 위와 같은 모양. id 는 서버가 매긴다(SP-005…)
```

⚠ **필드 정의는 사양서마다 다르다.** 프로토타입은 시드 4건만 mock 필드표(32개)를 갖고 새
사양서는 빈 표로 태어난다 — 서버도 같다(`fields: []`). 이 갈래가 없으면 "필드 정의를 채워
주세요" 안내와 남의 필드 32개가 같은 화면에 선다.

## 2. 결재 (Approval) — FR-114

### 요구사항 수용기준과 엔드포인트의 짝

| FR-114 수용기준 | 여기서 |
| --- | --- |
| ① 요청–승인–반려–재요청 전 경로 | `POST /api/approvals` · `POST /api/approvals/{id}/decide` |
| ② 승인선을 설정으로 변경 | `GET/PUT /api/approval-line` (**최대 3단계**, ASM-011) |
| ③ 각 단계에서 담당자에게 알림 | `GET /api/approvals?myTurn=true` (벨이 센다) |
| ④ 승인 이력 사후 조회 | 응답의 `trail[]` |
| ⑤ 조건부 분기 없음 | 결재선은 배열 하나 — 분기 필드를 두지 않는다 |

### 자원

```jsonc
// GET /api/approvals?state=진행 중&mine=true
[
  {
    "id": "APR-2026-0115",
    "kind": "사양서",                 // 사양서 | 배포 | 메뉴 | 권한
    "specId": "SP-001",              // kind=사양서 일 때만
    "deployId": null,                // kind=배포 일 때만
    "title": "VN7 엔진 사양서 v2.3",
    "version": "v2.3",
    "type": "수정",                   // 신규 | 수정 | 삭제 (재요청은 '수정')
    "urgent": true,
    "requester": "김민준",
    "requesterTeam": "IT 전략팀",
    "requestedAt": "2026.08.02",
    "deadline": "2026.08.07",         // 상신일 + 3일 (프로토타입 규칙)
    "waitingDays": 3,
    "step": [2, 2],                   // [지금 단계, 전체 단계]
    "approver": "김현대",             // 지금 차례의 결재자 — 단계가 넘어가면 함께 바뀐다
    "myTurn": true,                   // 서버가 로그인 사용자로 판단한다
    "state": "진행 중",               // 진행 중 | 승인 완료 | 반려 | 회수 | 취소
    "summary": "…",
    "changes": [{ "item": "최대 출력", "before": "285 hp", "after": "290 hp" }],

    // ⚠⚠ **상신 시점의 결재선을 건이 안고 간다.** 설정이 바뀌어도 이미 올라간 건은 안 바뀐다 —
    //    결재 중에 선이 움직이면 "누가 승인해야 했는가"가 사후에 달라져 이력이 못 믿을 것이 된다.
    "line": [
      { "seq": 1, "name": "한동현", "role": "IBD_APPROVER", "label": "검토" },
      { "seq": 2, "name": "김현대", "role": "IBD_ADMIN", "label": "최종 승인" }
    ],
    // 단계별 처리 자국 — 사후 조회의 실체
    "trail": [
      { "seq": 1, "approver": "한동현", "action": "승인", "at": "2026.08.03", "opinion": "" }
    ]
  }
]
```

### 조작

| 메서드 | 경로 | 본문 | 규칙 |
| --- | --- | --- | --- |
| POST | `/api/approvals` | `{ kind, specId?, deployId?, summary }` | 대상 상태도 함께 바뀐다(사양서 → `승인 대기`) |
| POST | `/api/approvals/{id}/decide` | `{ action, opinion }` | `action`=승인\|반려. **반려는 `opinion` 필수 → 없으면 400** |
| POST | `/api/approvals/{id}/withdraw` | — | 회수. 아래 규칙 참고 |
| POST | `/api/approvals/{id}/cancel` | `{ reason }` | 취소. **`reason` 필수 → 없으면 400**. 아래 규칙 참고 |
| GET/PUT | `/api/approval-line` | `[{ name, role, label }]` | 최대 3단계·빈 결재선 불가·**그 역할의 회원이 아니면 400** |

**승인은 단계마다 한 번씩이다.** 마지막 단계에서 승인이 나야 대상이 움직인다:
- `kind=사양서` → 사양서 `승인 완료`
- `kind=배포` → 배포 `진행중` + 그 배포에 실린 사양서들 `배포 완료`

**반려**는 어느 단계에서든 그 자리에서 끝난다 → 사양서 `초안` + `rejection` 기록.
요청자는 고쳐서 다시 `POST /api/approvals` 로 올린다(**재요청은 새 건**, `type: "수정"`).

**회수** (✔ **2026-08-19 채택** — FR-114 의 확장):
- 정의서의 "회수" 세 곳은 전부 *권한 회수*(FR-024·FR-030)라 원래는 요구사항 밖이었다.
  상신 직후 오타를 발견하는 실무를 보고 넣었고 그대로 쓰기로 정했다 — **요구사항
  추적표에 올릴 때 "정의서에 없던 확장"이라는 사실을 함께 적는다.**
- 조건: 요청자 본인이고 `trail` 이 비어 있을 때만. **한 단계라도 승인이 찍혔으면 409** —
  이미 판단한 사람의 기록이 사라지면 안 된다.

**취소** (동일 사양 다중 수정 요청 충돌 관리 — 2026-07-20 회의, 2026-08-21 구현):
- 겹친 요청 중 **채택되지 않은 것**을 결재자가 내린다. `state: "취소"` + `trail` 에
  `action: "취소"` 한 줄(사유 포함). **`reason` 없이는 400** — 남이 올린 요청을 내리는 일이라
  요청자가 나중에 이유를 읽을 수 있어야 한다.
- ⚠ **회수와 다르다**: 회수는 요청자 본인이 판단 전에만, 취소는 결재자가 **판단이 찍힌 뒤에도**
  할 수 있다(겹친 다른 건이 채택되면 이 건은 갈 곳이 없다). 자국은 지우지 않고 상태만 닫는다.
- ⚠ **자동 취소는 하지 않는다.** 하나를 승인하면 나머지를 서버가 알아서 내리게 만들 수도 있지만,
  그러면 사유가 "시스템 자동 취소"로 남는다 — 회의가 요구한 것은 사람의 판단과 그 이유다.

**겹침(conflict)** — 같은 `specId` 로 `진행 중` 요청이 둘 이상인 상태:
- **신청은 막지 않는다.** `POST /api/approvals` 는 그 사양서가 이미 `승인 대기` 여도 받는다
  (고객: "누가 먼저 했다고 다른 사람 걸 막느냐, 그건 안 될 것 같다").
  ⚠ 잠그는 것은 **문서 내용**이지 **요청**이 아니다 — 심사 중 본문 편집은 여전히 막는다.
- **막는 자리는 배포 하나뿐이다.** `POST /api/deploys` 는 실을 사양서 중 겹친 것이 있으면 **409**
  ("2개 이상이면 반영을 못하게 검증하는 것도 있어야겠다").
- **되돌리는 관문 하나**: 반려·회수·취소로 요청이 하나 내려갈 때, **남은 진행 중 요청이 0일 때만**
  사양서를 `초안`으로 되돌린다. 이 셈을 빼면 아직 심사 중인 건이 있는데 편집 잠금이 열린다.

## 3. 배포 (Deploy)

| 메서드 | 경로 | 뜻 |
| --- | --- | --- |
| GET | `/api/deploys` | 목록 |
| POST | `/api/deploys` | 배포 요청 — **'대기'로 태어나고, 같은 순간 결재 건이 생긴다** |
| GET | `/api/deploys/{id}` | 단건 |

```jsonc
// POST /api/deploys  { version, env, specs: ["SP-001"], changes: ["…"] }
// → 배포는 '대기', 승인자는 null(미정 — 0 이 아니라 미정이다)
{
  "id": "DEP-2026-0116", "version": "v3.1.2", "env": "Production",
  "status": "대기",                    // 대기 | 진행중 | 완료 | 롤백
  "specs": [{ "id": "SP-001", "name": "VN7 엔진 사양서", "version": "v2.3" }],
  "owner": "박준혁", "at": "2026.08.18 14:00", "scheduled": true,
  "durationMin": null, "approver": null,
  "approvalId": "APR-2026-0117"        // 함께 생긴 결재 건
}
```

⚠ **승인 없이는 배포가 시작되지 않는다.** 반려·회수된 배포는 목록에서 지우지 않고 `롤백`
자리로 남긴다 — "요청했다가 반려됐다"는 사실 자체가 배포 이력이다.

⚠ OPN-003: **'배포'의 대상 정의가 아직 미확정**이다(사양서 묶음인지, 릴리즈 단위인지).
지금 모양은 "사양서 여러 건을 실은 릴리즈"를 가정한다 — 확정되면 `specs[]` 의 뜻이 바뀔 수 있다.

## 4. 알림 (FR-114 ③)

벨은 **결재함이 세는 내 차례**를 읽는다(예전에는 화면이 `useState(3)` 로 들고 있었다).

```
GET /api/approvals?mine=true&state=진행 중   → 배지 수 = 길이
```

별도 알림 테이블을 만들지 않는 이유: 결재 알림의 정본은 결재함이다. 두 곳이 세면 배지와
목록이 다른 말을 한다(오늘 여러 번 겪은 병).

## 5. 옮길 때의 순서 (본개발 이관)

프런트는 **관문 뒤에서만** 서버를 안다. 화면을 고치지 않고 이 순서로 갈아끼운다.

```
1) data/specStore.ts      useSpecList()     → GET  /api/specs
                          registerSpec()    → POST /api/specs
2) data/approvalStore.ts  useApprovalList() → GET  /api/approvals
                          decideRequest()   → POST /api/approvals/{id}/decide
3) data/deployStore.ts    useDeployList()   → GET  /api/deploys
4) data/workflow.ts       상신·승인·회수의 **두 곳 동시 변경**을 서버 트랜잭션으로 옮긴다
                          (지금은 이 파일이 그 역할을 한다 — 서버로 가면 이 파일은 얇아진다)
```

⚠ 스토어는 서로를 부르지 않는다(순환 참조). 서버로 옮겨도 그 경계를 지킨다 — 결재가 사양서를
직접 고치는 게 아니라, **워크플로 한 곳이 둘을 함께 움직인다.**

## 5-1. 엑셀 이관 (FR-115)

사양서는 **지금 엑셀로 관리되고 있다** — 최초 이관은 파일로 들어온다. 템플릿·검증·부분 반영
정책과 화면 네 걸음은 `docs/엑셀_마이그레이션_설계.md` 가 정본이다. 서버로 옮길 때의 모양:

| 메서드 | 경로 | 뜻 |
| --- | --- | --- |
| GET | `/api/specs/import/template?kind=catalog\|fields` | 템플릿 파일(CSV/XLSX) |
| POST | `/api/specs/import/validate` | 파일 업로드 → **검증만** (행·열·사유 리포트 반환, 반영 없음) |
| POST | `/api/specs/import/apply` | 검증 통과 행만 반영 → `{ applied, skipped, failed, batchId }` |

⚠ 파일이 크면(열 수백·행 수만) **브라우저가 아니라 서버가 읽는다** — 프로토타입은 앞 200행만
표본으로 보고 행 수만 세지만(설계 §3-1), 서버는 전체를 본다. 그래서 `validate` 응답에는
`{ rows, sampled: false }` 처럼 **무엇을 다 봤는지**가 들어가야 한다.

⚠ 검증과 반영을 **가른다**: 사람이 "무엇이 들어갈지" 보고 나서 누르는 걸음이 있어야 한다
(지금 화면이 그렇게 돈다). `batchId` 는 본개발의 배치 되돌리기용이다.
